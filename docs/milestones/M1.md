# M1. CDC reader

Model: opusplan (Opus plans, Sonnet codes); review with opus | Time: week 1
Read first: docs/design.md (Key types: TxnBatch, Row), docs/concepts.md section 1

## Why
It is the only input. A change decoded wrongly makes everything after it wrong.

## How it works
1. Connect with replication=database.
2. Create the slot with pgoutput if it does not exist.
3. Start replication from an LSN with protocol version 1 and the publication name.
4. The server sends Relation, Begin, Insert, Update, Delete, Commit, and keepalives.
5. The client must send status updates, or the server disconnects it after wal_sender_timeout (60 s default).

## Task
- Build internal/cdc with github.com/jackc/pglogrepl, following .claude/rules/cdc.md.
- Decode int2/int4/int8, numeric, float8, text, varchar, bool, timestamptz, date.
- Fail loudly on Truncate, on an Update with no old tuple, on unknown types.
- For now acknowledge each transaction's end LSN after handing it to a callback. M8 changes this.
- cmd/deltaview flag --print-changes prints each TxnBatch.
- Integration tests against Docker Postgres: multi-row insert; update; delete; NULLs; numeric;
  timestamps; a 100 KB text column updated without changing it; one transaction touching two
  tables; a rolled-back transaction (must produce nothing); restart resumes without loss.

## Definition of done
All integration tests pass. The human watched live changes print while typing SQL in psql.

## Known traps
- Not answering keepalives.
- Accepting an Update with no old row.
- Ignoring the unchanged-TOAST marker and writing NULL.
- Parsing numeric as a float.

## Explain it back (for the human)
- What is a replication slot and its danger? A server-side bookmark; it pins WAL, so a dead consumer fills the disk.
- Why do changes arrive per transaction? Postgres decodes at commit and groups each transaction's changes.
- What happens to a rolled-back transaction? It is never sent.
