# M3. First view end to end, and the differential tester

Model: part A opusplan; part B opus for the whole session | Time: week 2 to 3
Read first: docs/design.md (Key types, HTTP API), docs/concepts.md sections 3 and 4, docs/testing.md
Do part A and part B in separate sessions.

## Why
A thin slice through the whole system proves the pieces connect. The tester then guards every later milestone.

## Part A task: the slice
- Filter and Project operators, the circuit runner, an in-memory state.Store, the apply loop.
- One view hard-coded in Go: SELECT id, amount FROM orders WHERE status = 'paid'
- Apply each TxnBatch, apply the output delta to the view store.
- Serve GET /views/paid_orders and GET /status (applied LSN and latest dv_heartbeat seq).

## Part B task: the tester
- Build cmd/dvtest following .claude/rules/tester.md.
- How it works: run a random transaction; bump dv_heartbeat.seq to N; poll /status until the
  engine reports N; run the view's SELECT on Postgres; read the view from DeltaView; compare as multisets.
- Views to check come from a list of (name, SQL) pairs.
- Flags: --seed, --txns, --check-every.

## Definition of done
- make difftest with 50 seeds of 1,000 transactions each: zero mismatches.
- Mutation check: make the filter ignore deletes. The tester must fail. Then revert.

## Explain it back (for the human)
- How do you know the engine is correct? It is compared with Postgres's own answer after random workloads, and planted bugs are caught.
- How does the tester know the engine caught up? Once the heartbeat change is visible, everything committed before it has been applied.
- Why multisets? Sets hide duplicate-row bugs.
