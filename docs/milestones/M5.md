# M5. SQL front end

Model: opusplan; opus review of the NULL logic | Time: week 5 to 6
Read first: docs/design.md (Supported SQL, Patterns)
Do the expression evaluator and the parser/planner in separate sessions.

## Why
Views should be written as SQL, not as Go code.

## How it works
```text
SQL text -> parse (pg_query_go) -> bind (names to column positions and types, from the
Postgres catalog) -> logical plan (Scan, Filter, Project, Aggregate) -> circuit
```

## Task
- Session 1: internal/expr. Three-valued logic and Postgres integer division. Unit-test against
  Postgres: for a table of expressions and input rows, our result must equal Postgres's result.
- Session 2: internal/sql. Read views.sql (CREATE MATERIALIZED VIEW name AS SELECT ...), parse,
  bind, plan, build the circuit. Support exactly docs/design.md "Supported SQL" except joins.
  Reject everything else with an error naming the feature.
- Replace hard-coded views with views.sql. Point the tester at the same file.

## Definition of done
The tester passes with at least 10 views from views.sql. A view with ORDER BY is rejected with a clear message.

## Known traps
- NULL = NULL treated as true.
- Integer division and implicit casts differing from Postgres.
- Unsupported SQL silently accepted.

## Explain it back (for the human)
- Logical plan vs circuit? The plan says what to compute; the circuit is the stateful operators that compute it.
- Why reject unsupported SQL? A wrong answer that looks right is worse than an error.
