# M6. Joins

Model: opus, effort high, whole session | Time: week 6 to 8
Read first: docs/concepts.md section 6, docs/design.md (State key layout)
Do the operator and the planner integration in separate sessions.

## Why
Joins are where hand-written incremental logic usually fails, and where this project earns its depth.

## Task
- Session 1: inner equi-join operator exactly as in .claude/rules/operators.md. Arrangements
  under j/OP/L and j/OP/R, keyed by encoded join key then encoded row. Unit tests from the
  worked example in docs/concepts.md section 6.
- Session 2: binder and planner for FROM a JOIN b ON a.x = b.y, with WHERE, GROUP BY and
  aggregates on top. Add tester views: orders joined to customers; revenue_by_city.
- Extend the workload: both tables changed in one transaction; a customer's city updated; a
  customer deleted while orders remain; duplicate join keys on both sides; NULL customer_id;
  an order's customer_id updated.

## Definition of done
50 seeds pass. Mutation checks: remove the dA join dB contribution; then double it. The tester must catch both. Then revert.

## Known traps
- Old index on both sides (drops dA join dB).
- New index on both sides (counts it twice).
- Matching NULL keys.
- Forgetting to multiply weights.
- int4 and int8 keys encoded differently, so equal keys never match.

## Explain it back (for the human)
- Derive the join delta from (A + dA) JOIN (B + dB).
- What does a join cost in state? A copy of both inputs, indexed by key.
- What about a hot key? Changing a customer with a million orders emits a million changes. Inherent, not a bug.
