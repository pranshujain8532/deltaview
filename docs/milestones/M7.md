# M7. Initial snapshot

Model: opus, effort high, whole session | Time: week 8 to 9
Read first: docs/concepts.md section 8, .claude/rules/durability.md

## Why
Real tables already contain rows when DeltaView first starts.

## How it works
1. On the replication connection, create the slot and export a snapshot. You get a consistent point and a snapshot name.
2. Keep that connection idle. The snapshot is valid only until the next command on it.
3. On a normal connection: BEGIN ISOLATION LEVEL REPEATABLE READ; SET TRANSACTION SNAPSHOT 'name'; read each table.
4. Feed rows through the circuits in chunks of 10,000, as +1 deltas. Never load a table into memory.
5. Write snapshot_done and applied_lsn = consistent point in one batch.
6. Start replication from the consistent point.

## Task
Implement the steps above. Handle an interrupted snapshot (snapshot_done missing at startup) by
wiping state, dropping the slot and starting again.
Test: load 1 million orders, start a background writer that never stops, start the engine, wait
for catch-up, pause the writer, run the differential check. Repeat 20 times.

## Definition of done
20 of 20 runs pass with the writer active during the snapshot.

## Known traps
- Reading tables on an ordinary connection instead of the exported snapshot.
- Running another command on the replication connection, which expires the snapshot.

## Explain it back (for the human)
- Why no gap and no double count? The snapshot sees exactly the commits before the point; the stream delivers exactly those after it.
- What if the engine dies mid-snapshot? It starts the snapshot again from nothing.
