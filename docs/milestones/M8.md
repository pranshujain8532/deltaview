# M8. Durable state and exactly-once

Model: opus, effort high, whole session; optional final review with fable | Time: week 9 to 11
Read first: docs/concepts.md section 7, docs/design.md (state interfaces, key layout)
Do the Pebble store and the crash testing in separate sessions.

## Why
Without it every restart means a full re-snapshot, and any crash risks double-applying changes.

## Task
- Session 1: a Pebble implementation of state.Store, one indexed batch per transaction,
  committed with sync. Move all operator state and view contents to it. Implement the apply
  loop exactly as in .claude/rules/durability.md. On startup read applied_lsn and start
  replication from it.
- Session 2: fail points chosen by an environment variable that exit the process: before
  commit, after commit before ack, after ack. A make crashtest script that runs the tester
  workload, kills the engine with kill -9 at random times, restarts it, then runs the full
  differential check. Detect a lost slot (wal_status = lost) and re-snapshot.

## Definition of done
200 random kill cycles under load, then a clean differential check. Each fail point passes alone.

## Known traps
- Acknowledging before the commit.
- Committing without sync.
- Operators caching state in struct fields that drifts from the store after a failed batch.

## Explain it back (for the human)
- Walk through the three crash points in .claude/rules/durability.md.
- Why fsync? Without it the OS may hold the write in memory; a power cut loses it after you acknowledged.
- What if the slot is lost? Postgres deleted WAL you needed. Only a new snapshot is correct.
