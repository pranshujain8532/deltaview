# M9. Serving and subscriptions

Model: opusplan; review with opus | Time: week 11 to 12
Read first: docs/design.md (HTTP API), docs/architecture.md (Concurrency)

## Why
A live view is only useful if clients can read it and follow its changes.

## How it works
- GET /views/NAME reads from a store snapshot, so it sees one consistent LSN.
- Subscribe: the request goes to the apply loop. Between two transactions the loop takes a
  snapshot and registers the subscriber in one step. The client gets the snapshot with its
  LSN, then every delta after it.
- Each subscriber has a bounded buffer. On overflow the server sends a resync event and closes.
- Every delta carries its LSN, so a reconnecting client can ignore what it already has.

## Task
Build internal/serve as above. The apply loop must never block on a subscriber.
Tests: a client that applies the snapshot and all deltas must equal GET /views/NAME at the same
LSN under concurrent writes; a stalled client is dropped and throughput is unaffected.

## Definition of done
Both tests pass under load.

## Explain it back (for the human)
- How does a subscriber never miss or repeat a delta? Snapshot and registration happen at one LSN; deltas carry LSNs.
- Is delivery to subscribers exactly-once? No. At-least-once with LSNs; clients drop duplicates.
